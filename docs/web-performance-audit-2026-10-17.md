Браузерные и серверные показатели нельзя складывать как независимые составляющие одного измерения.

## Варианты с потенциалом более 10%

### 1. Не вызывать помощь расшифровки при точном совпадении с эталоном — первый приоритет

`TranscriptionService.transcribe` вызывает assistance для любого разрешённого текста при включённой настройке, даже если он уже совпадает с canonical/variants. `AnswerAnalyzer` при этом уже умеет обходиться без AI при точном совпадении. До assistance можно добавить аналогичную консервативную проверку с сохранением диакритики и исходного transcript. Не расширять совпадение до fuzzy similarity и не подменять ошибочный ответ эталоном. Согласовать безопасное состояние assistance/receipt и покрыть оба языка и изменения transcript тестами.

Измеренный **аналог удалённого ожидания** — сравнение существующей настройки on/off на эталонах: 259,21 → 148,93 мс, **−42,5%** суммарно; STT 221,50 → 107,83 мс, **−51,3%**. Это ещё не A/B новой реализации: ветка оптимизации не написана. При 0 мс на mock AI соответствующий полный путь 55,33 → 48,20 мс (**−12,9%**), но малую разницу нельзя переносить в production. Эффект для всего трафика зависит от доли точных ответов при включённой помощи; если выигрыш на подходящих запросах 42,5%, для >10% в среднем они должны давать >23,5% исходного времени ожидания.

Помощь можно выключить существующей настройкой: на синтетических альтернативах 365,56 → 252,60 мс (**−30,9%**), но теряются её подсказки. Автоматически отключать её всем пользователям не предлагается.

### 2. Уменьшить structured output анализа, сохранив объяснения ошибок

Сейчас модель генерирует corrected_sr, alternatives, общую короткую/подробную обратную связь, issues с отдельными explanation и demonstrated_skills. Часть затем корректируется backend: canonical presentation, pronunciation, fluency, skill completion. Проверить компактную внутреннюю Pydantic-схему и детерминированное восстановление действительно вычисляемых полей. Сохранить смысловые отличия допустимых вариантов и все объяснения ошибок RU/EN; просто удалить подробности или снизить качество — не ускорение того же продукта.

Порог: если AI занимает долю `f` задержки проверки, сокращение его времени на `r` даёт `f × r` общего выигрыша. В synthetic alternative без помощи AI занимает примерно 100 / 144 = 69%; уменьшение его задержки на 20% дало бы около **14%** проверки. Это расчёт, не измеренный выигрыш новой схемы. Для полного цикла в этом mock-примере доля анализа около 100 / 253 = 40%: нужно >25% сокращения анализа для >10% цикла.

[Официальные рекомендации OpenAI](https://developers.openai.com/api/docs/guides/latency-optimization) предлагают уменьшать число выходных токенов и количество последовательных запросов. Конкретный процент для SerboTalk требует сравнения реальных token counts, latency и точности на одинаковом наборе фраз. Уменьшение одного только лимита токенов не равно уменьшению фактического ответа.

### 3. Кэшировать повторный семантический разбор, а текущие timing/scoring считать заново

При повторении одних фраз одинаковые альтернативные ответы снова вызывают модель. Возможен ограниченный owner-scoped кэш **валидированного семантического результата**, с ключом source/canonical/variants/transcript/skills/язык/версия prompt и schema/model env; инвалидировать при изменении любого значимого входа. Не кэшировать готовый AttemptResponse, daily limit, штрафы подсказок, learner updates, voice timing или итоговый балл. Сейчас timings передаются модели: до введения кэша нужно явно отделить их от семантики, иначе результаты неэквивалентны.

При попадании может исчезнуть почти весь model wait. Иллюстрация по нашим замерам: проверка альтернативы с 100 мс AI 144,28 мс против 41,43 мс с нулевым AI wait — потенциал около **71% на cache hit**, а не доказательство реализации кэша. Для >10% среднего времени проверки при таком эффекте нужен time-weighted hit rate >14%. Реальная доля повторов неизвестна; прежде измерить числовой hit-rate без сохранения аудио/приватных логов. Кэш внутри serverless-процесса теряется при cold start и не общий между instances; хранение и retention требуют отдельного решения.

### 4. Потоковая расшифровка во время речи

Сейчас MediaRecorder накапливает chunks, `finish()` формирует один Blob и лишь затем загружает его. `start(500)` не отправляет звук на сервер каждые 500 мс и не означает обязательное ожидание 500 мс после Stop. Обработка во время записи может перекрыть upload/STT речью. Отдельный прототип нужен для совместимости модели, короткоживущей browser-сессии, очистки аудио, качества и восстановления ошибок; постоянный ключ только backend.

Условие >10% ожидания после Stop: скрытая часть upload/STT должна превышать 10% исходного времени до финального transcript/результата. Это **не измерено**, диапазон процентов обещать нельзя. Streaming готового файла улучшает время до первого частичного текста, но сам по себе не гарантирует более быстрый полный transcript или валидированный результат. [Официальная документация по transcription](https://developers.openai.com/api/docs/guides/transcription) разделяет обработку файла и живого потока. В рамках аудита Realtime/WebRTC не добавлялись.

### 5. Убрать ненужное ожидание при первом показе тем/подготовке

`App.tsx` ожидает `Promise.allSettled(topics, reviewSummary)` перед выбором начального сценария. Медленный summary задерживает готовность обычных тем. Можно показать доступные темы сразу и догрузить счётчик; автоматический выбор повторения нужно сохранить так, чтобы поздний ответ не перезаписывал ручной выбор/новую сессию. Для >10% стартовой задержки требуется, чтобы сэкономленное ожидание summary составляло >10% startup critical path. У нас mock запросы занимают единицы миллисекунд, поэтому **измеренного >10% эффекта здесь нет**.

## Что уже ускорено и что не доказано

- Start уже объединяет сессию и первую фразу в один API-запрос. Каталог выдаёт встроенные фразы без LLM; говорить об ускорении их «генерации» моделью неверно.
- Следующая фраза уже prefetch-ится после успешной проверки, пока пользователь читает результат. Повторно предлагать этот механизм как новую оптимизацию не нужно.
- Эталонные ответы уже анализируются локально. Нельзя засчитывать это в новый выигрыш.
- Обновления topics/summary после проверки уже фоновые. Уменьшение числа этих запросов может снизить нагрузку, но не гарантирует >10% latency текущего результата.
- Генератор считает Scheduler targets до выбора каталожной фразы, после чего заменяет targets данными каталога. Это кандидат на локальную чистку CPU/ORM, но >10% end-to-end не измерено.
- Большой JS chunk влияет на первый вход при медленной сети; code splitting не ускоряет серверную расшифровку или анализ. Загрузка English-каталога должна оставаться доступной без рассинхронизации языков.
- Меньший bitrate уменьшит upload, но может ухудшить STT. Доказанного >10% нет. Сейчас уже используется сжатое аудио, 64 kbit/s.
- Модель/регион/pooler/cold start могут доминировать в production; смена модели без замеров качества не подтверждённая оптимизация. Model IDs задаются env. Убирать grounding-check/retry ради скорости не предлагается.
