# Мягкая помощь распознаванию — проект на ревью, 03.10.2026

Статус: только проект. Не реализовано и не входит в APK с доработками интерфейса. Включение возможно только после личного ревью владельца.

## Предлагаемое поведение

После распознавания пользователь видит текст, в котором безопасные орфографические артефакты уже исправлены. Изменённое слово имеет ненавязчивое подчёркивание: нажатие показывает «Распознано: allergičan → Написание: alergičan» и позволяет вернуть исходный вариант. Под ответом краткая подпись «Уточнено написание: 1 слово». Текст остаётся редактируемым; проверка запускается только зелёной галочкой.

Для неоднозначных звуков и окончаний показываем предложение «Возможно, čemu?» / «Возможно, …e?». Оно не применяется само: пользователь выбирает предложенный или исходный вариант либо записывает снова. Если подтверждение не получено, проверяется исходный текст.

Рекомендую начать с двух уровней: автоматически исправлять только проверенные артефакты написания; спорные фонетические и грамматические места уточнять у пользователя. Это проектное решение, а не обещание точности распознавания.

## Что можно исправлять

| Ситуация | Действие | Ограничение |
| --- | --- | --- |
| allergičan → alergičan | Автоматически с видимой отметкой и отменой | Только целая словоформа из проверенного разрешённого списка; никакого общего удаления двойных согласных |
| alergican → alergičan | Предложить написание | Диакритика может обозначать другой звук; автоматический режим только для отдельно проверенного однозначного слова |
| cemu / ćemu → čemu | Предложить и запросить выбор | č / ć — фонетическое различие; написание по тексту не доказывает правильного произношения |
| Окончания i / e | Только предложение с подтверждением | Возможна настоящая ошибка числа, падежа или согласования |
| Пропущенное слово, отрицание, число, другое время или лексема | Не исправлять автоматически | Сохраняем смысл и учебную ошибку |
| Уже допустимый вариант перевода | Оставить | Не подгонять свободный ответ к единственной канонической фразе |
| Ручной ввод или отредактированный текст | Не менять без действия пользователя | Помощь относится к новой расшифровке; поздний ответ не перезаписывает ввод |

## Поток и границы доверия

1. Текущий STT возвращает исходный transcript. Никакой второй записи и хранения аудио: только существующий временный буфер в памяти; освобождение после STT.
2. Сервис TranscriptionAssistance получает текст, каталог разрешённых вариантов написания, язык и упражнение. Сначала локальная проверка разрешённых орфографических замен; неизвестное слово автоматически не исправляется.
3. Опциональный AI-проход предлагает спорные места структурированным JSON. Полный правильный ответ не передаётся в STT prompt: это увеличило бы риск подстановки ответа вместо распознавания. Контекст задания можно использовать в отдельном проходе только для предложений с подтверждением.
4. Pydantic валидирует JSON, а сервис проверяет границы правок, исходный фрагмент, отсутствие перекрытий, разрешённый тип и предел числа замен. Полный переписанный ответ от модели не принимается. При timeout, неверном JSON или недоступности возвращается исходный текст без блокировки тренировки.
5. UI показывает исходный текст и применённые/предложенные замены. Идентификатор записи и revision черновика защищают от поздних ответов при повторной записи, редактировании, смене упражнения и выходе.
6. При зелёной галочке backend использует только серверно проверенную редакцию: предложение не влияет на scoring без подтверждения. Клиент не может объявить произвольную замену «орфографической».

OpenAI допускает prompt для контекста и предпочтительного написания в поддерживаемых transcription-моделях. Это подсказка распознавателю, а не гарантия достоверности или оценка произношения. Поддержку prompt и дополнительных сигналов нужно проверять именно для настроенной env-модели. Источник, проверен 03.10.2026: [официальная документация Speech to text](https://developers.openai.com/api/docs/guides/speech-to-text#prompting). Для проекта дополнительно использован навык OpenAI Docs.

В текущем adapter уже есть инструкция дословной транскрипции без исправления слов. Её не меняем в этом релизе. Если после ревью понадобится помощь на этапе STT, новый prompt должен храниться отдельным версионированным файлом; потребуется отдельная проверка, что контекст не повышает ложную правильность.

## Предлагаемый контракт и хранение

Только спецификация, без создания API/таблиц в этом изменении:

- `transcription_id`, `exercise_id`, `revision`, `policy_version`.
- `raw_text`: исходный transcript; `display_text`: результат разрешённых правок.
- `changes[]`: `start`, `end` (индексы Unicode code points, преобразование в UTF-16 на frontend), `original`, `replacement`, `kind` (`orthography_artifact` / `phonetic_ambiguity` / `ending_ambiguity`), `action` (`applied` / `suggested`), `reason_code` из закрытого списка.
- `confidence` — только необязательный вспомогательный сигнал, не доказательство произношения и не единственный критерий автозамены. Числовые пороги определять по оценке качества, а не угадывать.
- Ручное подтверждение/отмена привязано к серверной правке и revision; список ограничен, например тремя спорными фрагментами на ответ. Предел уточнить на ревью.

Два текстовых представления и валидированный журнал применённых изменений допустимы в БД. Никаких бинарных данных и пользовательского аудио в БД, файлах, логах или fixtures. Если храним новый контракт, меняем SQLAlchemy и Alembic вместе с понятным downgrade. В логах — только технические счётчики/длительность/ошибки без текста пользователя.

## Scoring и обучение

Автоматический орфографический артефакт не штрафует перевод. Подтверждённое фонетическое/морфологическое предложение маркируется как помощь: в первом выпуске такая попытка не увеличивает mastery/perfect streak и не переводит фразу в «выучено». Семантическая обратная связь показывается, но отдельная отметка «С подсказкой» объясняет ограничение. Следующая самостоятельная попытка снова участвует в mastery. Это предлагаемая политика и важный пункт личного ревью: иначе подсказка маскирует ошибки и завышает прогресс.

Произношение не оцениваем по тексту: исходная расшифровка уже является интерпретацией STT. Нет изменения Scheduler/Learner Model до согласования политики. Каталог навыков остаётся закрытым, новых skill_key модель не создаёт.

## Внедрение после согласования

- По умолчанию feature flag выключен; модель только из env; короткий timeout, ограниченный retry, safe fallback и версионированная схема.
- Сначала небольшой вручную проверенный список орфографических артефактов и предложение/отмена в UI; отдельный AI-проход — второй этап, если качество первого недостаточно.
- Автотесты используют только искусственно составленные текстовые примеры и mock ответов AI. Регрессии: двойная l, корректное удвоение в имени, диакритика, i/e, отрицания/числа, альтернативный перевод, пустой STT, неверный JSON, late response, отмена, два алфавита, неподтверждённые предложения, защита mastery и подмена клиентского журнала.
- Метрики на согласованном наборе: доля точных правок, доля скрытых настоящих ошибок, доля отмен, лишняя задержка. Главный стоп-критерий — любая подтверждённая автоматическая смысловая или морфологическая подмена в контрольном наборе. Расширение разрешённого списка только после проверки.
- Реальные речевые случаи можно проверять вручную без сохранения записей. Без аудиокорпуса текстовые тесты проверяют политику правок, но не доказывают акустическую точность.

- [ ] Утвердить автоматическое исправление только разрешённых орфографических артефактов с отменой.

- [ ] Утвердить отсутствие роста mastery для попыток с принятой фонетической/грамматической подсказкой.
