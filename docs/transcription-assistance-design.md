# Мягкая помощь распознаванию — analysis-v3, 05.10.2026

По прямому поручению владельца система переработана: фиксированный словарь исправлений
и локальная политика local-v1/v2 заменены анализом каждой расшифровки. Предыдущее
согласование первого словаря больше не является требованием этой реализации.

## Поведение

Когда мягкие подсказки включены, после каждого успешного STT выполняется отдельный
структурированный AI-анализ текста, в том числе для точного совпадения с эталоном.
Передаются русский источник, исходная расшифровка, канон и допустимые варианты.
Модель рассматривает все расхождения, оценивает близость написания/звучания и
правдоподобие искажений распознавания. Она может учитывать корректную альтернативную
формулировку, даже если она отсутствует в сохранённом списке вариантов.

Нет заранее заданных слов и пар замен. Для любого слова возможна гипотеза о
диакритике, удвоении/пропуске букв, похожих звуках, сегментации или спорном окончании.
Правильные синонимы, порядок слов, пол говорящего и естественные варианты перевода
не исправляются ради совпадения с каноном. Настоящие лексические, смысловые и явные
грамматические ошибки остаются для обычной проверки ответа.

Все новые предложения требуют подтверждения и допускают отмену; автоматических
замен от модели нет. Показана короткая причина возможного искажения. Нет ограничения
на три подсказки: рассматриваются все фрагменты в пределах лимита transcript 1200
символов. Каждая правка локальна (до трёх слов / 120 символов), полный ответ модель
не переписывает. Эти пределы ограничивают размер одной правки, а не число подсказок.

## Границы достоверности

Анализ получает текст, а не аудио. По тексту нельзя доказать плохое качество записи,
конкретную ошибку STT или правильное произношение. Формулировки обозначают гипотезу.
Это не акустическая оценка; новая запись и хранение аудио не добавляются.

## Серверный контракт

Версионированный prompt: `backend/app/prompts/transcription_assistance_v3.md`.
Ответ AI валидируется `TranscriptionAssistanceAnalysis` и `TranscriptionCandidate`:
`acceptable_variant`, `candidates[]`; для каждой гипотезы точный `original`, номер
вхождения `occurrence_index`, `replacement`, `kind`, `plausible_stt_error`,
`preserves_meaning` и `explanation_ru`. Никакого разбора свободного текста.

Сервис проверяет точное вхождение на границах слов, размер локального фрагмента,
сохранение чисел и отрицания, допустимую письменность, отсутствие перекрытий и
лимит итогового текста. Отдельно вычисляет близость букв после NFC/латинизации,
общего удаления диакритик, сравнения без пробелов и алфавитного folding đ/dj:
нормированное расстояние Левенштейна. Не принимаются слишком далёкие замены
(расстояние больше max(1, длина / 3 с округлением вниз)); для форм до двух букв
требуется совпадение после folding. Это консервативная инженерная эвристика, не
калиброванная вероятность. Близость сама по себе не достаточна: обе оценки модели
о вероятном STT-искажении и сохранении смысла также должны быть положительными.
Набор грамматических маркеров отрицания используется только как запрет изменения
смысла и никогда не генерирует замены. Словаря исправлений нет.

API сохраняет прежние `text`, `raw_text`, `transcription_id`, `policy_version`,
`changes[]`. Для новых изменений `action=suggested`; дополнительные поля —
`explanation_ru` и `similarity`. `assistance_status=analyzed` означает завершённый
анализ, а не правильный ответ. `unavailable` показывает safe fallback: исходный
текст доступен для проверки, редактирования и повторной записи. Отсутствие API key,
text model, timeout, refusal, невалидный JSON/фрагменты не блокируют успешный STT.
На fallback receipt не создаётся. Старые receipts остаются валидными.

## AI, хранение и жизненный цикл

Анализатор использует `OPENAI_TEXT_MODEL` и backend-only `OPENAI_API_KEY`.
Отдельные env `OPENAI_ASSISTANCE_TIMEOUT_SECONDS=6` и
`OPENAI_ASSISTANCE_MAX_RETRIES=0` задают короткий bounded budget; допустимы timeout
до 12 секунд и максимум один retry. Дополнительный вызов добавляет задержку и
расход API только при включённых подсказках. STT prompt не содержит полного канона
и не меняется. Запрос Responses использует Pydantic Structured Outputs, `store=False`.

Буфер аудио и upload stream освобождаются сразу после STT, до текстового анализа.
Аудио не сохраняется в файлах, БД, логах или fixtures. В receipt разрешены только
текст и валидированные правки. Текущие JSON-поля позволяют хранить новые метаданные
без изменения SQLAlchemy/Alembic-схемы. Request/draft epochs защищают повторную
запись, смену упражнения, уход и ручное редактирование от позднего результата.

## Проверка ответа

Индексы подтверждённых правок проверяются по серверному receipt и владельцу.
После публикации PR #77 от 08.10.2026 принятие STT-подсказки не ограничивает Learner Model,
mastery, серию правильных ответов и интервал повторения: исправленный текст оценивается
обычным анализатором. Верный ответ даёт обычный прогресс; оставшиеся ошибки учитываются.
transcription_assisted остаётся только метаданными, без штрафа или блокировки прогресса. Отмена возвращает
исходный фрагмент. Ручное редактирование останавливает применение кнопок и сохраняет
доказательство уже принятой помощи. Scheduler, каталог skill_key и обычная оценка
произношения по тексту не расширяются.

## Проверки и выпуск

[Checkpoint](transcription-analysis-checkpoint.md) разделяет локальную реализацию,
публикацию, Android-перенос и ручную приёмку. Автотесты используют только искусственные
тексты и mock AI. Они проверяют протокол и защиту, а не акустическую точность модели.
Реальная речь и качество выбранной env-модели требуют отдельной ручной проверки.

Контракт проверен через OpenAI Docs 05.10.2026:
[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses),
[Speech to text](https://developers.openai.com/api/docs/guides/speech-to-text).
Structured Outputs предоставляет формат/схему, а не гарантию верной интерпретации;
STT-подсказки способны повлиять на результат, поэтому полный канон передаётся
последующему анализатору, а не в STT prompt.
