# Правила проекта Serbian Speaking Trainer

## Область действия

Правила действуют для всего репозитория. Реализуй проект небольшими вертикальными срезами и оставляй приложение запускаемым после каждого этапа.

## Неизменяемые ограничения

- Никогда не сохраняй пользовательское аудио в БД, файлах, логах или тестовых fixtures. Допустим только временный буфер в памяти, который освобождается после получения transcript/timing events.
- `OPENAI_API_KEY` существует только в backend-окружении. Не передавай постоянный ключ в browser, frontend bundle или API response.
- Все OpenAI model IDs задаются только через env. Не зашивай модели, aliases, цены и даты в бизнес-логику.
- Любой программно используемый LLM output валидируется Pydantic-схемой. Не разбирай свободный текст регулярными выражениями.
- OpenAI adapter, Scheduler, Learner Model и scoring живут в сервисах; API routers только валидируют/оркестрируют вызовы.
- Для внешних AI-вызовов обязательны timeout, ограниченный retry, безопасная ошибка и mock в автоматических тестах.
- До полного текстового вертикального цикла (этапы 0–5) не добавляй WebRTC/voice.
- Перед Realtime/WebRTC сверяй контракт с актуальной официальной документацией OpenAI. Постоянный ключ остаётся на backend; browser получает только короткоживущие параметры/сессию.
- Не добавляй Docker, Redis, PostgreSQL, очереди или микросервисы без уже существующей необходимости. MVP использует SQLite.
- Не позволяй модели автоматически расширять каталог навыков неизвестными `skill_key`.

## Архитектура и данные

- Зависимости направлены `api -> services -> repositories -> db`; бизнес-правила не зависят от FastAPI.
- SQLAlchemy-модели и Alembic-миграции меняются вместе. Миграции должны быть повторяемыми и иметь понятный downgrade.
- В БД разрешены текстовый transcript, числовые timing metrics и валидированный structured analysis JSON; бинарное аудио запрещено.
- Prompts хранятся отдельными версионируемыми файлами.

## Проверки и документация

- Для бизнес-логики добавляй unit tests, для API/БД — integration tests, для UI — component test, typecheck и production build.
- Тесты не должны вызывать OpenAI и расходовать API budget.
- После значимого этапа обновляй `README.md` и `docs/decisions.md`; не описывай будущие возможности как готовые.
- Сохраняй несвязанные пользовательские изменения. Не коммить `.env`, SQLite-файлы, секреты, build artifacts и зависимости.
- После каждой завершённой доработки публикуй затронутые web-приложение и backend в облачный production через принятый GitHub/Vercel workflow. Дождись состояния Ready и проверь соответствующий production URL и изменённый сценарий. Если публикация заблокирована, явно сообщи причину и не называй задачу завершённой.

## Web-first и Android-релизы

- Согласованная Android-версия нового релиза — `1.15` (`versionCode 25`), после `1.14`. Факт сборки и проверки фиксируется в `docs/p1-testlab-checkpoint.md`; предыдущие контрольные выпуски — в `docs/android-1.14-release.md` и `docs/p0-checkpoint.md`. Обычные доработки web-приложения не меняют Android `versionCode`, `versionName`, имя APK или версию в `package.json`.
- Не синхронизируй Android-проект, не собирай APK и не повышай Android-версию без отдельной явной команды пользователя.
- Дорабатывай и проверяй функции сначала в web-приложении. Изменения, которые должны войти в будущий Android-релиз, накапливай в `docs/android-release-backlog.md`.
- По команде на Android-релиз перенеси и проверь весь накопленный набор, после чего согласуй следующий номер версии отдельно.
- Не переходи на версию `2.0` или любую версию `2.x` без отдельного явного указания пользователя.
- Имя каждого собранного APK формируй строго по шаблону `SerboTalk-andorid16-<версия>.apk`. Написание `andorid16` является частью шаблона и не исправляется.

## Команда агентов и контрольные этапы

- Основной агент-оркестратор — GPT-6.1 Sol с уровнем рассуждения «Среднее» (`gpt-6.1-sol`, `medium`), как задано в `.codex/config.toml`. Модели исполнителей выбираются по их ролям.
- Оркестратор отвечает за постановку задач, актуальность базы, согласование API, распределение файлов, интеграцию и выпуск. Он не подменяет независимое ревью своим утверждением.
- Для реализации аудита явно разрешена команда: backend и frontend — GPT-6 Sol; воспроизводимые проверки и документация — GPT-6 Luna; независимое ревью рискованных изменений — GPT-6.1 Sol с уровнем рассуждения «Среднее». Настройки ролей находятся в `.codex/agents/*.toml`.
- Одновременно запускай не более трёх исполнителей плюс оркестратор. Давай агенту короткое задание с абсолютным workspace, границами файлов, контрактом, критериями приёмки и требуемым отчётом. Передавай только необходимый контекст.
- Один файл имеет одного активного владельца. Агент не меняет чужую область, не создаёт вложенных агентов, не коммитит и не публикует без явного поручения оркестратора.
- Сначала сравни рабочую базу с актуальным remote main. Сохраняй незакоммиченные пользовательские изменения; для отдельной базы используй управляемый worktree.
- Снимай исходные проверки до правок. После реализации выполняй целевые тесты, общий quality gate и независимое ревью стабильного diff. Исправляй подтверждённые замечания до релиза.
- Экономь лимиты через узкие задачи, повторное использование агента и краткие отчёты; не запускай нескольких агентов на одну реализацию и не повторяй полные проверки без новой причины.
- Основной актуальный план аудита — `docs/audit-roadmap.md`. После каждой завершённой задачи отмечай выполненное через `[x]`, оставшееся через `[ ]` и записывай дату, результаты проверок и ссылку на PR/коммит или документ с доказательствами. Частично выполненный пункт разделяй на завершённую и оставшуюся части. Реализацию, публикацию, Android-сборку и ручную приёмку отмечай отдельно; не закрывай весь P0/P1/P2 до выполнения всех его обязательных пунктов. `docs/audit-improvement-plan.md` сохраняет исходную постановку и состав команды, а не параллельные статусы.
- По поручению владельца от 2026-09-29 после завершения P0 и P1 выполняются контрольный web/backend production deploy и Android-сборка для ручной проверки. Это разрешение на контрольные сборки; номер следующей Android-версии по-прежнему согласуется отдельно, до изменения версии и сборки.
- На контрольной точке предоставь URL, commit SHA, APK, результаты автоматических проверок и короткий сценарий ручной приёмки. Дай владельцу проверить этап перед переходом к следующему большому разделу.
- Уже выпущенные решения (голосовой ввод, выбор сербского алфавита, мгновенные подсказки и объединённый старт) сохраняй. Методические правила и лимиты не меняй под видом ускорения.

## Тестовая среда и измерения

- Автономный вход выполняется только в изолированном testlab через подписанную сессию локального Supabase-совместимого провайдера. Не добавляй production bypass, универсальные пароли или выдачу чужой идентичности. Production OAuth и реальный STT проверяются отдельно.
- Локальные данные, секреты и отчёты testlab хранятся только в игнорируемых `.env.testlab` и `artifacts/testlab`. Пользовательские базы не сбрасываются для замеров. Инструкция: `docs/testlab.md`.
- Android-варианты `prod` и `lab` имеют раздельные assets и идентификаторы приложения; lab-сборка не меняет production assets. Перед выпуском проверяй APK и web bundle на отсутствие тестового входа и локальной конфигурации.
- В тестах отключай HAR, trace, видео, снимки и автоматические DOM/ARIA-контексты ошибок, способные сохранить пароль, токен или аудио. Отчёты содержат только обезличенные маршруты, размеры, статусы, длительности и счётчики.
- Сравнения до/после выполняй последовательно на одинаковых снимках тестовых данных и с одинаковыми параметрами. Указывай платформу, режим AI, прогрев и размер выборки; задержку команд агента не используй как метрику приложения.
